# Uploads and copies between servers

RemoteFiles can send a file to a server from this device, or copy a file from one server to another. Both are things you ask for, one file or batch at a time: browsing, reading, searching and downloading still never write to a server.

- **Upload:** in a remote folder, choose **Folder actions → Upload Files…** and pick one or more files, or **Upload Photos…** to pick photos and videos from the library. On iPad you can also drag files from another app onto the folder. The photo picker is the system's own: it shows the library without RemoteFiles being given access to it, and hands over only what you choose, as the original's bytes in its own format and under its own name.
- **Copy:** touch and hold a file and choose **Copy to Server…**, pick a server (the file's own server is offered too) and a folder, then tap **Copy Here**. The bytes go from the first server, through this device, to the second; nothing is stored on the device.

Starting a transfer leaves the folder you started it from on screen. A ring in the folder's navigation bar fills as the server confirms bytes, turns into a tick for a few seconds when the queue has finished, and into an orange mark when a transfer needs attention. A file that arrives in a folder on screen appears there without a refresh, in every window showing that folder and not only the one the transfer was started in. Tapping the ring opens **Transfers**, which lists every upload and copy with **Cancel**, **Retry** and **Remove**; once the list has something in it, Home shows the same button beside Settings. **Clear Finished** removes completed and cancelled entries (one cancelled a moment ago goes once it has stopped, so that its partial file is still removed from the server), and **Delete All** cancels what is running and empties the list. Files already sent stay on their servers.

Only regular files are sent. Folders can't be uploaded or copied yet, and a copy takes one file at a time.

## What is written, and where

A file is written under a hidden name in the destination folder, `.rf-upload-<identifier>.part`, and is given its real name only once every byte is there. Nothing that reads the folder meanwhile, a web server or a backup job, sees half a file under the name you chose.

- The destination folder must still resolve to exactly the path you chose it at, checked before the partial file is opened and again once every byte is there, before it is named. A folder that has been replaced by a symbolic link leading elsewhere is refused. As for downloads, SFTP has no way to open a file relative to an open folder, so this catches a folder durably replaced, not one swapped for an instant.
- The partial and final names are single names inside that folder. A name with a slash, a control character or more than 255 bytes is refused before anything is sent.
- The partial file is created exclusively, so the server makes a new file and never writes through a name planted there. Anything already under a partial name that this transfer didn't write, including a symbolic link, is removed and never written through.
- The source's modification time is kept where the server allows setting it.
- A copy's source is bounded by the folder it was chosen from, exactly as a download is: the file and its folder must still resolve to the canonical paths you chose.
- A copy's source must be the same file at the end as at the start. Its size and modification time are read as it is opened and again once it has been read, and a copy of a file that changed meanwhile is refused and never named. A file written over at the same length with its time put back can't be told apart this way.

## Names that are already taken

Before anything is sent, a name the folder is known to hold is asked about: **Replace**, **Keep Both** (the new file gets a number: `notes 2.txt`), or, when other files were chosen with it, **Skip**. Dismissing the question sends nothing.

The server has the last word when the file is named. A name that turned out to be taken, by a file that appeared while the upload ran or one the listing didn't show, is not written over: the transfer stops as **Name Taken** with its bytes kept on the server, and **Replace** or **Keep Both** in Transfers then only names them. Nothing is sent twice. How firmly the server can refuse a taken name depends on the folder, as the next two paragraphs say: in one step where hard links are available, and with a brief gap where they aren't.

Without Replace, a file takes its name by a hard link (`hardlink@openssh.com`), which the server refuses in one step if the name exists, and its partial name is then removed. That holds whatever the server's own rename does with a taken name.

Where hard links aren't available, because the server lacks the extension or the folder is on a file system without them (exFAT, some network shares), SFTP has no operation that refuses a taken name in one step, and RemoteFiles looks at the name and then renames. That leaves an instant in which a file someone else creates under the same name can be replaced, on any server:

- OpenSSH's rename normally makes a hard link itself and refuses a taken name. On a file system without hard links it too checks the name and then renames over whatever is there, so the instant is the one between its own check and its rename.
- A server whose rename replaces an existing file outright, against the SFTP specification, leaves the whole round trip between RemoteFiles' look and its rename.

This is the one case in which a file can be replaced unasked. It needs a folder without hard links and another writer creating that exact name at that moment. The alternative would be to refuse every upload to such a folder.

**Replace** swaps the file in one step on servers with OpenSSH's `posix-rename@openssh.com` extension, which is nearly all of them. On a server without it, the old file is first moved aside under a hidden name of the transfer's own, `.rf-upload-<identifier>.old`, the new file is named, and only then is the old one removed; for a moment the name is absent. If that stops part-way, the old file is still on the server, under its name or the hidden one: Retry finishes the replacement, and Cancel or Remove puts the old file back under its name if nothing else has taken it. A file already moved aside is never moved over. A folder is never replaced by a file. Replacing a symbolic link replaces the link, not what it leads to, and that holds for a link to a folder too: the link goes and the folder stays.

## Interruptions and Retry

A transfer interrupted by a lost network, Disconnect, the app going to the background or a crash keeps its partial file on the server, and Transfers shows how much was sent. After the app has been closed in the middle of a transfer, that figure is the one saved up to two seconds before, so it can be a little short of what the server holds; Retry measures the server's copy and not the figure. **Retry** continues from the end of those bytes only if all of these hold:

- the source still has the size and modification time it had when the partial file was written;
- the partial file is a regular file no longer than the source; and
- its final 64 KiB equal the source's bytes at the same offsets.

Otherwise it starts again from the first byte. As for [downloads](DOWNLOADS.md#resuming-interrupted-downloads), a rewrite of the source that keeps its size within one modification-time tick, away from where the transfer stopped, can't be told apart without sending everything.

**Cancel**, **Remove**, and a refusal that Retry would only repeat (permission denied, a missing or redirected folder, a source that changed) remove the partial file from the server. If the server can't be reached then, a hidden `.rf-upload-….part` file stays in the folder; it is safe to delete. The same is true of one left beside a finished file, if the server named the file and then refused to remove the partial name: it is a second name for that file, not a second copy.

An upload's file is copied into the app when you choose it and deleted once it has been sent or removed from the list. Its private folder is excluded from backups and protected like the download folder. A copy keeps nothing on the device.

## Limits

| | Limit |
| --- | --- |
| One uploaded file | 16 GiB, and it must fit on the device while it waits |
| One copied file | 64 GiB |
| Entries in Transfers | 500; finished ones make room for new ones |

One transfer runs at a time, beside the download queue, which has its own. A transfer stops after 60 seconds without the server confirming any bytes, and ends about 5 seconds after that limit or a cancellation even when the network has gone.

## Connections and background behavior

Uploads and copies use SSH connections of their own, one for each server a transfer reaches, separate from browsing and from downloads. A connection, and one SFTP channel on it, stays open while the queue has work for that server, so a batch of files pays for one handshake and one channel, and both close when the queue is empty. Each transfer still uses the host keys you trusted and the keys you unlocked. A transfer that meets a host key to verify or a key to unlock shows the prompt a download would; the folder chooser for a copy shows no prompts, and asks you to open that server from the library first.

Background behavior is the download queue's: the transfer under way may go on when you switch apps or lock the device; queued transfers wait for the app to return. A transfer with 8 MiB or more still to move, or of unknown size, asks iOS for a continued processing task as it starts. A copy's size is the file's as the copy starts, not as its folder's list had it. iOS shows that task in its own way, which the app does not control: on the iPad it was tested on, as a banner at the top of the screen that covers the folder's title and buttons until it is swiped up and away, after which a small indicator stays in the status bar and the transfer goes on. The banner came up for three or four seconds even for a copy over in under a second, so a transfer with less than 8 MiB to move normally asks for no task as it starts. It holds the short time iOS gives any app to finish what it is doing as it leaves the screen, which shows nothing; where iOS gives none, it asks at once. Every two seconds it is looked at again, and if the app is in front and it is not under ten seconds from its end at the rate it has kept since the last look, it asks for the task then. The cost is one case: a transfer of under 8 MiB that the device is locked on, or the app left, before iOS has handed the app a task for it. That is so before its first look, after looks that found it near its end, and after a look that asked where iOS has not yet answered or has refused. iOS refuses a request made once the app has left the screen, and the app turns down a task that arrives then, so that transfer has only the short time. If it is too slow to finish in that time, or stops moving, the transfer is interrupted when the time runs out, its row saying so, and **Retry** continues it from what was sent. iOS does not say how long the short time is. The three figures are choices, not measurements. The larger transfer asks as it starts, while the app is in front; asked for then, the tested copies went on and finished with the device locked, on an iPhone and an iPad. Asking only as the app leaves the screen was tried on the iPad, in two builds: it kept the banner away and a copy still went on behind the Home Screen, but every copy locked by a press of the side button stopped, three in all, and iOS's answer to the request, recorded in two of them, was "the required application is not in the foreground". A transfer that stops when the device is locked is the worse fault, so the larger transfer keeps its banner ([what was tried](REAL_SERVER_ACCEPTANCE.md#21-november-2026-transfers-on-ipad)). The list of transfers is protected while the device is locked, so it can't be saved then. What a transfer does meanwhile is written to a second file, `transfers-unsaved.json`, of a kind iOS lets an app create while locked and closes to reading again once written; the list itself is saved when the app is next in front, or when iOS says protected files can be reached again if that is later, and the second file is then removed. If the app is closed first, the next launch opens whichever of the two was saved later, so a copy that finished while the device was locked is listed as finished. Each file carries a count that rises with every save, and the later is known by that and not by the files' dates: a second file that outlived the save meant to remove it is older by its count whatever the clock says, and is not opened. A second file that is there and can't be read, as when the app is started on a device still locked, may be the later, so the queue is not opened at all then, and nothing is swept or saved over; uploads and copies are unavailable until the app is next started. If neither file can be written, as on a full disk, the change is held in memory and saved when a save next succeeds, and is lost if the app is closed first. Explicit Disconnect interrupts the queue. Editing or removing a connection, or forgetting a host key, interrupts only the transfers that use it, as either end of a copy. Removing a connection removes its transfers from the list. A transfer made for a connection that has since changed can't be retried; start it again.

A server or account can refuse writes altogether, for example OpenSSH's `internal-sftp -R`. An upload to it fails with the server's refusal and changes nothing.

A copy to another folder of the same server reads the file over the channel it writes on, so it works on a server that allows one channel at a time. A copy between two servers uses one channel on each.

## Speed

Writes are pipelined: 32 requests of 32 KiB are in flight at first and up to 128 once the connection has shown what it delivers in a round trip, as a download's read window grows. Each confirmation counts as it arrives, so a slowly supplied file still shows progress and isn't taken for one that has stopped. A copy reads from one server a window ahead of what the other has confirmed, so a slow destination holds the source back and a few mebibytes at most wait in memory.

A file in a queue costs about seven round trips beyond its bytes: checking the folder, creating the partial file, the close, the link that names it, removing the partial name, and little else, because the channel is already open. Through a loopback proxy adding the delay shown, on a MacBook Air (M3), each a median of three to five runs ([how](PERFORMANCE.md#uploads-and-copies-21-november)):

| | 40 ms | 150 ms |
| --- | ---: | ---: |
| Upload 50 B, in a queue | 283 ms | 939 ms |
| Upload 3 MiB, in a queue | 369 ms | 1,267 ms |
| Copy 3 MiB between two connections, in a queue | 612 ms | 2,052 ms |
| Download 3 MiB, for comparison | 510 ms | 1,737 ms |

The first file of a queue also pays for the connection and its channel. On a simulator against a loopback OpenSSH server, a 200 MiB copy between two connections took about two seconds. On an iPhone 17 Pro over Tailscale to the same kind of server, a 64 MiB upload ran at 7.3 MiB/s and a copy between two connections at 6.7 MiB/s, where a download ran at 11.0 MiB/s, each using a few megabytes of memory. That path, between two wireless devices, is what set those rates: on an iPad over it, an upload ran at 11.5 MiB/s beside a download's 13.0 and a plain TCP stream's 8.6, and over loopback on the Mac uploads run at about 800 MiB/s and downloads at about 950 ([details](PERFORMANCE.md#uploads-and-copies-21-november)).

## Validation

`SFTPUploadIntegrationTests` runs against the isolated OpenSSH fixture: exact bytes and modification time, no leftover partial file, an empty file, a taken name refused before any byte is sent, Keep Both and Replace, a name taken mid-transfer answered without a second transfer, naming by hard link and, with links switched off, by looking and renaming (a dangling link still holds its name either way), a folder never replaced, a link to a folder replaced as a link, replacing without `posix-rename` (an attempt that had stopped half-way, one whose name was taken again meanwhile, putting the old file back on removal, and a symbolic link), continuing an interrupted upload only while source and partial file match, a slowly supplied file, a connection closed under a transfer without cancelling it (it fails within seconds and does not wait), a queue sharing one channel, a planted link under the partial name, a redirected or missing folder, a folder moved away during the transfer with a link left in its place, invalid names, removal limited to the app's own partial names, a copy between two connections that both stay open, resumes, and refuses a source outside its folder and one written over at the same length while it was read, and a copy within a server started with `MaxSessions 1`. The instant between a server's own check and its rename can't be hit on demand; that is covered only by reading the code. The [compatibility suite](SERVER_COMPATIBILITY.md#uploads-on-other-servers-22-november-2026) runs an upload check against other servers as well: OpenSSH 8.2, ProFTPD, SFTPGo and AsyncSSH, the last also without the two extensions and with a rename that replaces a taken name, and it has every read-only server refuse an upload with nothing left behind. `TransferManagerTests` covers the queue: staging and cleanup, one connection for a batch, kept versions across relaunch, progress saved while a transfer runs so that a relaunch still shows what was sent, a list that couldn't be saved being saved when the app returns and read back at the next launch if the app was closed first, the later of the list and the file beside it being opened whatever their dates say and neither when the file beside it can't be read, Name Taken, partial-file removal on cancel and refusal, Clear Finished while a cancelled transfer is still stopping or a finished one is closing its connection, copies, a copy whose source had grown since it was listed, interrupting one connection's transfers, Disconnect, the background, and name rules. `AppModelTransferTests` covers the window: taken names left out or answered, a finished upload refreshing its folder in every window, connection edits and removals, what a drag hands over (files copied out under their own names; links, a link that comes with a name and its address as text, and selected text left out), a dropped file that can't be read being told apart from something that isn't a file, that a folder's list takes a drop only while the folder can take an upload, on a row as on the space below the rows, with anything else left to the list's own delegate, and that a drop target stays on its own screen's list through a push and a pop and never takes another screen's.

`AppModelTransferTests` covers the rule for background time with stand-ins for iOS's short time and for the clock: a transfer of under 8 MiB asks for no task and holds the short time until it ends; one with more to move, or of unknown size, asks as it starts; a short one is looked at every two seconds and asks only once it is not near its end at the rate it has kept, or has stopped moving, and never while the app is away; when the short time runs out the transfer is interrupted, its row saved so, before the time is given back, in the stand-in queue and in the upload queue itself; one transfer ending as the next starts gives back the first's time before taking the second's; and where iOS gives no short time, a short transfer asks for a task; and the line the Transfers and Downloads sheets end with says what holds for the transfer under way, goes back to its idle wording when that ends, and keeps "iOS stopped" until the next transfer starts. With protected data made unavailable to a real download queue, it checks that the queue reports a download whose bytes have all arrived as a success, and one that failed not; that the app then told iOS so, with a task granted, was seen on a device. iOS handing over the task, or refusing it, can't be made to happen in a test. It also covers the window's side of a lock: one that passes through active on its way to the background leaves the window, and both queues, in the background, with nothing told to connect again; a return that another leaving has overtaken is not acted on, and the return after it waits for both closings. `TransferManagerTests` and `DownloadManagerTests` cover an interruption being in the saved list before its connection has closed, and a download whose interruption could not be saved still opening as interrupted.
